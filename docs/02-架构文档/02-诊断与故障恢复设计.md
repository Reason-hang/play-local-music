## 问题与目标

旧实现会在崩溃后启动不可取消的邮件弹窗，并读取整机 `logcat`；用户可被困在弹窗中，日志还可能包含超出本应用排障需要的内容。目标是保留可复现证据，同时不阻塞退出、不恢复网络权限、不自动对外发送数据。

## 方案对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 保留强制邮件和全量 logcat | 修改最少 | 锁死、隐私边界差、离线语义冲突 | 淘汰 |
| 接入远程崩溃平台 | 聚合方便 | 需要网络、隐私告知和服务治理 | 不适用离线 MVP |
| 本地有界结构化记录与主动导出 | 可离线排障、最小权限、可控存储 | 需要用户导出和真机复现 | 采用 |

## 当前实现

- 未捕获异常由 `DiagnosticStore` 先写入私有崩溃摘要，再交还平台异常处理器；不启动邮件 UI。
- 普通事件以 JSONL 写入 `events.jsonl`，最多 200 条或约 128 KB；崩溃文件最多 20 份，每份最多 64 KB。
- “设置 → 诊断与日志”可列出崩溃摘要、清除记录、主动生成 ZIP 并调用系统分享。
- 播放错误写入模块、错误码和消息；不记录媒体标题、完整本地路径、URI、剪贴板或用户输入。

## 隐私与性能约束

诊断不需要 `INTERNET` 或额外存储权限。崩溃写入使用原子文件；普通事件有上限且失败只写 Log，不阻塞播放。导出只读取应用私有目录，用户未点击前不会创建可分享文件。

## 故障恢复流程

1. 崩溃后重新打开应用，进入“设置 → 诊断与日志”。
2. 查看最新摘要，记录复现动作与时间。
3. 点击“导出诊断包”，在系统分享面板中自行选择去向。
4. 修复后保留一份导出包对照，确认后在诊断页清除本地记录。
