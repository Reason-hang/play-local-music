# 断点续播失效审计报告

审计日期：2026-08-15；修复复核：2026-08-16。审计基线：`4adeeee fix: restore video progress across entry points`；修复版本：1.7.1。审计方式：静态调用链审查与定向单元测试；修复复核未替代红米真机验收。

## 修复复核结论

`VR-003` 与 `VR-004` 已在 1.7.1 修复：队列加载会请求播放服务在替换时间线前保存当前视频、解析目标视频位置；首页、分类、搜索等自定义命令会保留媒体展开后的真实 `startIndex`，不再把原始点击位置误当成展开后的目标位置。`VR-002` 的可观测性缺口已部分修复：诊断现在能够区分恢复成功、无记录、目标项变更和播放器已推进后的保护性跳过。

`VR-005` 仍由既有 `MediaSession.addToCommandQueueThenFlush()` 串行化后续播放命令，未发现需要扩大修改面的证据。`VR-006` 的 1 秒保护阈值保留，用于避免覆盖用户已经主动开始播放或 seek 的位置；现在会写出跳过原因，真机若持续出现该事件再以日志证据决定是否调整阈值。所有结论均不等于 Redmi/HyperOS 已通过端到端验收。

## 1. 一页式风险总览

| 结论 | 证据等级 | 影响 |
| --- | --- | --- |
| 1.6.2 的“视频 A/B 均从 0:00 开始”有明确根因：保存和读取使用单一身份键，携带路径与仅携带 `MediaStore ID` 的同一视频无法匹配。 | 已证实 | 直接导致跨首页、分类、搜索、队列的续播记录查找失败。 |
| 1.6.3 已改为同时保存 `id:` 和路径哈希，两个变体的存储层测试各 7/7 通过。 | 已证实 | 修复了 1.6.2 的身份不一致问题，但仅证明存储层。 |
| 1.6.3 的真实端到端续播仍未被证明。队列恢复依赖异步回调，首页/搜索命令丢弃扩展后的起播索引，诊断也不会记录“为什么没有恢复”。 | 静态分析，待真机验证 | 仍可能出现“记录存在但实际从 0:00 播放”。 |

当前最没有把握的事情不是数据能否保存，而是：**在 Redmi/HyperOS 上，每个入口最终是否对目标视频执行了 `seekTo(已保存位置)`。** 现有代码与单测均不足以证明这一点。

## 2. 审计范围和未覆盖范围

已审计：`VideoResumeProgressStore`、`GramophonePlaybackService`、`QueueBoard`、`EndedWorkaroundPlayer`、`LibraryTreeLoader`、`SongAdapter`、诊断事件和续播单测。

未覆盖：Redmi 24122RKC7C 的实际安装状态、两份 1.6.3 APK 的点击链路、锁屏/全屏/系统回收、媒体库重扫后的真实 `MediaItem` 内容。当前环境无 `adb` 命令且无连接设备，不能把构建或 Robolectric 测试写成真机结论。

## 3. 技术栈和模块概览

应用使用 Kotlin、Media3/ExoPlayer、`MediaSessionService` 和应用私有 `SharedPreferences`。续播状态由 `VideoResumeProgressStore` 保存；首页、分类、搜索等通过 `MediaController.sendCustomCommand()` 请求服务替换播放队列；队列板通过 `QueueBoard.commitQueue()` 直接替换 ExoPlayer 时间线。

## 4. 严重问题清单

### 问题编号：VR-001

问题标题：1.6.2 对同一视频仅保存单一身份键，跨入口会查不到已保存进度。

风险等级：P1。

问题类型：功能正确性、数据一致性。

置信度：高，已由 1.6.2 源码直接证实。

影响模块：`VideoResumeProgressStore`、首页/分类/搜索/队列的 `MediaItem` 传递链路。

故障根因：1.6.2 的 `fingerprint()` 优先取文件路径哈希；当播放器或队列对象在 MediaSession 传递后只保留 `MediaStore ID` 时，保存记录为 `id:MediaStore:<id>`，后续从扫描列表重新打开时却按路径哈希查询。两把键没有映射关系，查询必然返回空值。

代码证据：

```kotlin
// 1.6.2：只返回一把键
val key = getFile()?.absolutePath?.let(MediaIdentity::pathKey)
    ?: mediaId.takeIf(String::isNotBlank)?.let { "id:$it" }
```

文件路径：`app/src/main/java/org/akanework/gramophone/logic/library/VideoResumeProgressStore.kt`（提交 `a2d71cc`）。

代码行号：历史版本第 69–74 行。

调用链：扫描对象/队列对象 → 播放服务 `saveCurrentVideoProgress()` → `VideoResumeProgressStore.save()` → 下一入口 `resumePosition()`。

触发条件：同一 MP4 在“带 `EXTRA_FILE` 的扫描对象”和“仅有 `mediaId` 的播放器/队列对象”之间切换。

复现步骤：播放视频 A 至超过 5 秒；切至视频 B；重新从扫描首页、分类、搜索或队列打开 A。

复现结果：静态推导为键不一致，`records[fingerprint.key]` 返回 `null`。

实际表现：用户在 1.6.2 已报告 A/B 均从 0:00 开始。

预期表现：同一视频无论从哪个入口打开，恢复该视频独立保存的位置。

影响范围：1.6.2 的两个应用变体；不影响 MP3 播放本身，但让视频断点续播不可用。

安全影响：无远程攻击面。

业务影响：核心承诺“每个视频独立断点续播”失效。

数据影响：进度记录可能已经保存，但无法被另一入口读取；不涉及手机源文件。

性能影响：无明显性能影响。

利用难度：不适用，正常使用即可触发。

是否可远程利用：否。

是否需要登录权限：不适用，本地离线应用。

修复建议：1.6.3 已采用正确方向：同一条记录同时以 `id:<mediaId>` 和路径哈希保存、查询时尝试两把键。

短期止血方案：升级并实际安装 1.6.3；旧版只存路径哈希而新入口只有 ID 的历史记录不可逆，需在 1.6.3 中将视频再播放并切换一次，写入双键记录。

长期治理方案：把“媒体身份别名集合”作为存储层唯一入口，禁止业务层自行选择单一键；为 MediaSession 序列化前后对象加入集成测试。

验证方式：两变体 `VideoResumeProgressStoreTest` 于本次审计中各 7/7 通过，其中含“扫描对象带路径、播放器对象只有 ID”双向恢复用例。

回归测试要求：真机按首页、MP3/MP4 筛选、分类、搜索、队列五条入口分别打开 A；A/B 各等待至少 15 秒后切换并验证恢复位置。

修复优先级：已修复代码，P0 真机验收。

修复依赖：必须安装 versionCode 35、versionName 1.6.3 的同一应用变体。

当前残余风险：1.6.3 的新记录可双键匹配；但旧 1.6.2 单键历史记录无法在缺失原始键时反向推导。

### 问题编号：VR-002

问题标题：端到端恢复未被测试或观测，构建成功和存储单测通过不能证明用户点击后实际跳转到保存位置。

风险等级：P1。

问题类型：交付验证缺失、可观测性缺失。

置信度：高，已证实测试范围不足；具体真机失败链路待验证。

影响模块：`GramophonePlaybackService`、`QueueBoard`、`SongAdapter`、诊断与交付验收。

故障根因：测试只直接调用 `VideoResumeProgressStore.save()/resumePosition()`；项目没有 `androidTest` 目录，也没有覆盖 MediaSession 自定义命令、队列加载、`Player.Listener` 回调及实际 `seekTo()` 的测试。诊断事件仅在成功恢复后写入 `video_resume_restored`，保存被跳过、查找未命中、回调被保护条件拦截时均无记录。

代码证据：

```kotlin
val positionMs = videoResumeProgressStore.resumePosition(item) ?: return@post
player.seekTo(positionMs)
DiagnosticStore.recordEvent(... event = "video_resume_restored")
```

文件路径：`app/src/main/java/org/akanework/gramophone/logic/GramophonePlaybackService.kt`。

代码行号：第 1777–1796 行；测试文件为 `app/src/test/java/org/akanework/gramophone/logic/library/VideoResumeProgressStoreTest.kt` 第 34–118 行。

调用链：用户点击 → 自定义 MediaSession 命令/队列加载 → ExoPlayer 时间线替换 → `onMediaItemTransition()` → `restoreVideoProgressIfNeeded()` → `seekTo()`。

触发条件：任何入口在服务异步处理、媒体准备、切换回调或条件保护中断恢复。

复现步骤：按用户的 A 12:35 → B 03:20 → 从首页、分类、搜索、队列重开 A/B 的矩阵执行，并导出“诊断与日志”。

复现结果：当前不能从诊断包区分“未保存”“键不匹配”“未触发 transition”“保护条件跳过”或“seek 后被后续命令覆盖”。

实际表现：1.6.2 已失败；1.6.3 尚无真机证据。

预期表现：每一次保存、查询、跳过和成功恢复都有脱敏事件；验收可证明实际 seek 位置。

影响范围：两个 APK；一旦某个入口失效，用户会认为全部续播功能未实现。

安全影响：无远程攻击面；新增事件必须保持现有脱敏策略，不记录路径和标题。

业务影响：无法快速定位失败根因，形成重复交付后才由用户发现的问题。

数据影响：可能存在记录而未使用；不影响 MP3、队列和手机源文件。

性能影响：若每 15 秒都记录详细日志会膨胀；应只记录切换、查询、恢复、拒绝原因，不记录周期性保存成功。

利用难度：不适用，正常操作即可暴露。

是否可远程利用：否。

是否需要登录权限：不适用。

修复建议：服务层把续播决策收敛为一条可返回结果的逻辑，返回 `SAVED`、`SKIPPED_TOO_EARLY`、`CLEARED_FINISHED`、`NOT_FOUND`、`IDENTITY_MISMATCH`、`APPLIED` 等脱敏状态；诊断只记录状态和秒数，不记录标题、URI、路径。

短期止血方案：先在红米执行固定 A/B 验收矩阵，并一键复制诊断摘要；将 `video_resume_restored` 是否出现、恢复秒数是否正确作为硬验收门槛。

长期治理方案：新增服务级集成测试或 Android instrumentation 测试，使用真实 MediaSession/测试播放器验证“入口命令 → 目标 item → seekTo”的完整链路。

验证方式：现有定向单测仅证明存储层，不能替代本问题验证；本机无 ADB/设备，未完成。

回归测试要求：两变体均跑五入口 A/B 矩阵、应用退后台、锁屏、任务移除、强制结束后重开；每步比对诊断事件。

修复优先级：P0，下一次打包前必须闭环。

修复依赖：连接 Redmi 或可用 Android 16 模拟器；新增最小服务级测试和诊断事件。

当前残余风险：在未取得真实事件时间线前，任何“已修复”均只能表示源码层修复，不表示用户设备行为已验收。

## 6. 安全问题清单

审计结论：未发现续播功能引入网络、权限、源文件删除或明文路径外发问题。`VideoResumeProgressStore` 仅存位置、时长、修改时间和哈希化路径键；现有 `DiagnosticStore` 会清洗路径和内容 URI。

仍存在的限制：后续添加续播诊断时不得把 `mediaId`、文件标题、绝对路径直接写入事件或复制摘要。

## 7. 性能与稳定性问题清单

审计结论：定时保存间隔为 15 秒，且存储上限为 500 条、180 天，规模适合个人本地播放器。未发现全量扫描或高频日志导致的直接性能阻断。

仍存在的限制：诊断补强应避免对每次 15 秒保存写一条事件；只记录状态变化和失败原因。

## 8. 架构与可维护性问题清单

审计结论：存储层已与 MP3 队列恢复分开，方向正确；但“决定目标项、确定续播位置、替换时间线、开始播放”分散在服务、队列板、适配器和播放器包装层，导致同一产品规则有多条路径。

建议：不做架构重写，只在 `GramophonePlaybackService` 增加一个内部统一入口，供自定义命令和队列加载复用；UI 仅发送用户意图，`QueueBoard` 不直接决定视频起播位置。

## 9. 数据一致性问题清单

审计结论：1.6.3 的双键保存解决了当前对象“有路径/无路径”的一致性；文件替换通过时长与修改时间使旧记录失效。旧 1.6.2 单键记录不能在缺失旧键时自动迁移，这是数据模型的物理限制，不是新版本继续写错。

建议：升级说明中明确：首次升级到 1.6.3 后，需要各播放一次目标视频并切换，才能补齐旧记录的双身份别名。

## 11. 上线阻断项

在没有完成 1.6.3 的真实 A/B 跨入口验收前，不能把“断点续播已可靠交付”作为发布结论。若 1.6.3 真机仍从 0:00 开始，VR-003 至 VR-006 中至少一项将转为已复现缺陷，必须先按 P0-2/P0-3 修复后再打包。

## 12. 建议观察项

- 两个应用是不同 package，应用私有续播记录天然隔离；若用户希望“本地听歌”和“多听课程”共享同一视频进度，这是未做过的独立产品决策。
- 系统强杀无法保证回调执行，当前目标是最多损失 15 秒，而不是零丢失；需要在真机压力场景验证。
- 接近结尾 30 秒内会清除记录并从头播放，这是“已看完”的既定规则，必须在验收样本中避开该区间。

## 13. 可接受的残余风险

在不重构播放器的前提下，MediaStore ID 和路径哈希都可能因文件移动、重建媒体库而变化；当两者同时变化时，旧进度应安全失效并从 0:00 播放，不能猜测性地套用到可能不同的文件。此风险可接受，优先保证不会恢复到错误视频。

## 14. 最终审计结论

1.6.2 的根因已确认：单身份键导致跨入口无法匹配。1.6.3 的双键存储修复在两份应用的存储单测中通过，但它不是端到端验收。当前最大的遗漏是把“保存正确”误当成“所有入口都会恢复正确”，同时没有给失败路径留下可复制的证据。下一步应先用 1.6.3 真机矩阵获得事件证据；若仍失败，则按本报告的统一服务入口、队列直连恢复、索引和异步顺序修复，不再重复只改存储层。
